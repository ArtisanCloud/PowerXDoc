# 角色与对象

* **开发者（Developer）**：打包并提交插件。
* **市场（Plugin Market 服务）**：保存插件/版本元数据，托管构建文件（S3/MinIO），签发下载链接。
* **宿主（PowerX）**：查询版本、下载安装、校验完整性。

核心数据对象（MVP 版）：

* **Plugin**：插件档案（ID/Name 等）。
* **PluginVersion**：版本记录（Version/Channel/MinCore/ReleaseNotes + `SHA256`/`Size`/`StorageKey`）。

    * 注：MVP 把构建信息（sha256/size/storageKey）放在 Version 上；进阶可拆 `Artifact` 多平台构建。
* **Download**：下载审计。

# 环境准备（一次性）

1. **配置**（`etc/config.yaml`）

    * `database.dsn` 指向唯一的 PostgreSQL 实例/库。
    * `storage` 指向 MinIO/S3：

        * `endpoint`: `http://127.0.0.1:9001`（如果你把 API 改在 9001）
        * `bucket`: `bucket.px-plugins`（你当前的桶名）
        * `use_path_style: true`（桶名含“.”必须开）
    * `auth`：

        * 开发期可 `disabled: true`；或配置 `dev_token: "dev-123456"`

2. **建表**（一次）

   ```bash
   go run ./cmd/database migrate
   ```

3. **（可选）种子数据**
   仅建议 seed Developer/Plugin；**不要 seed 版本**，避免和正式发布混淆。

   ```bash
   go run ./cmd/database seed
   ```

4. **启动服务**

   ```bash
   go run ./cmd/marketd
   ```

5. **MinIO 就绪检查**

   ```bash
   curl -s http://127.0.0.1:9001/minio/health/ready
   # ready
   ```

# 上架发布流程（开发者视角）

> 目标：把插件 `com.example.promo@1.0.0` 正式上架，让宿主可下载。

## 阶段 A：申请上传（创建存储位置）

* **接口**：`POST /v1/dev/uploads`
* **鉴权**：需要 `Authorization: Bearer <dev_token>`（或关闭鉴权）
* **请求体**：

  ```json
  { "plugin_id":"com.example.promo", "version":"1.0.0", "os":"linux", "arch":"amd64" }
  ```
* **响应**：

  ```json
  {
    "upload_url": "http://<minio-api>/<bucket>/<path>.pxp?...X-Amz-...",
    "storage_key": "s3://bucket.px-plugins/com.example.promo/1.0.0-linux-amd64.pxp"
  }
  ```
* **动作**：把 `upload_url` 保存好，下一步要用它上传**二进制包**。

## 阶段 B：上传构建产物（真正把文件放到对象存储）

* **命令**：

  ```bash
  dd if=/dev/urandom of=/tmp/promo-1.0.0.pxp bs=1 count=256      # 演示用
  curl -i -X PUT -T /tmp/promo-1.0.0.pxp "<upload_url>"
  # 期望：HTTP/1.1 200 OK
  ```
* **注意**：

    * 必须用 **PUT**，且 `upload_url` 要整条复制（带所有 `X-Amz-*` 参数）。
    * 有效期默认 900 秒；过期就重新申请上传链接。

## 阶段 C：登记版本（写入数据库元信息）

* **先计算校验值**：

  ```bash
  # macOS
  SHA=$(shasum -a 256 /tmp/promo-1.0.0.pxp | awk '{print tolower($1)}')
  SIZE=$(stat -f%z /tmp/promo-1.0.0.pxp)
  ```
* **接口**：`POST /v1/dev/plugins/:plugin_id/versions`
* **请求体**（MVP 把构建信息写在 Version 上）：

  ```json
  {
    "version":"1.0.0",
    "channel":"stable",
    "sha256":"<上面的SHA>",
    "size":256,
    "storage_key":"s3://bucket.px-plugins/com.example.promo/1.0.0-linux-amd64.pxp",
    "min_core":"1.0.0",
    "release_notes":"Initial release"
  }
  ```
* **响应**：

  ```json
  { "status": "ok" }
  ```
* **数据库变化**：

    * `plugins`：如果不存在，会自动创建（OwnerDevID=当前开发者）。
    * `plugin_versions`：插入或更新一条 `(plugin_id, version)` 的记录，并保存 `sha256/size/storage_key`。

## 阶段 D：验证上架（可供宿主发现）

* **列版本**：

  ```bash
  curl -s http://localhost:8080/v1/plugins/com.example.promo/versions | jq
  ```

  看到 `1.0.0` 且包含 `SHA256/Size/StorageKey` 即成功。
* **查“最新可用”版本（建议给宿主用）**：

    * **接口**：`GET /v1/plugins/:plugin_id/latest?channel=stable&core=1.0.0`
    * **返回**：一条兼容 `core` 的最新版本记录（MVP 用 `min_core <= core` 简比较；进阶用 semver）。

# 安装下载流程（宿主视角）

## 阶段 E：申请下载（获取签名 URL）

* **接口**：`POST /v1/downloads`
* **请求体**：

  ```json
  { "plugin_id":"com.example.promo", "version":"1.0.0" }
  ```
* **响应**（MVP）：

  ```json
  {
    "signed_url": "http://<minio-api>/<bucket>/...pxp?...X-Amz-...",
    "sha256": "be1177c6...",
    "size": 256,
    "expires_at": "2025-08-19T..."
  }
  ```

## 阶段 F：下载与校验（宿主执行）

1. 下载：

   ```bash
   curl -L -o /tmp/promo-download.pxp "<signed_url>"
   ```
2. 校验：

   ```bash
   shasum -a 256 /tmp/promo-download.pxp
   # 与响应里的 sha256 比对；不一致则拒绝安装
   ```
3. 安装：宿主的安装逻辑（解包、落入插件目录、写 manifest、触发重载等）。

# 流程时序图（文字版）

```
开发者 → Market: POST /v1/dev/uploads
Market → 开发者: {upload_url, storage_key}
开发者 → MinIO: PUT <upload_url> (二进制)
开发者 → Market: POST /v1/dev/plugins/:id/versions (登记 + sha256/size/storage_key)
Market → 开发者: {status: ok}

宿主 → Market: GET /v1/plugins/:id/latest?channel=stable&core=1.0.0
Market → 宿主: 版本元信息
宿主 → Market: POST /v1/downloads {id, version}
Market → 宿主: {signed_url, sha256, size}
宿主 → MinIO: GET <signed_url> (下载)
宿主: 校验 sha256 → 安装
```

# 常见分叉与设计取舍

## A) 单构建 vs 多构建

* **MVP（当前）**：一个版本一个构建 → 把 `sha256/size/storageKey` 放 `PluginVersion`。
* **进阶**：一个版本多构建（OS/ARCH）→ 新增 `Artifact` 表；下载时带 `os/arch` 查选定构建。

## B) 是否需要人工“审核/上架”步骤

* MVP：登记即上架（`Visibility=published`）。
* 进阶：加状态机（`draft → submitted → approved → published`），再开审核接口/后台。

## C) 版本兼容判断

* MVP：`min_core <= core`（字符串比较足够填坑用）
* 进阶：用 semver（`github.com/Masterminds/semver`）解析比较，支持范围表达式。

## D) 鉴权

* 开发期：`auth.disabled: true` 或 `dev_token`
* 生产：OIDC/JWT（建议接入，控制开发者/租户角色与权限）

# 快速自检清单（踩坑排雷）

* **PUT 成功了没？** 看 MinIO 返回 `HTTP/1.1 200 OK`。
* **DSN 一致吗？** psql 一定要用 `config.yaml` 的同一 DSN 连接。
* **下载报 “artifact not found”？**

    * 你现在用的是 MVP：请确保 `/v1/downloads` 用的是 `PluginVersion.StorageKey`，**不要查 Artifact**。
* **/versions 返回里 Plugin 是空对象？** 正常，因为没 `Preload("Plugin")`；如果不需要，给模型加 `json:"-"` 隐掉。

# 你现在“下一步就该做”的两件事

1. **把“查最新版本”接口加上**（`GET /v1/plugins/:id/latest?channel&core`），方便宿主只传 `plugin_id` 就能拿到可用版本。
2. **宿主端接下载→校验→安装**：先用脚本跑通，再接到 PowerX 的插件安装器里。
